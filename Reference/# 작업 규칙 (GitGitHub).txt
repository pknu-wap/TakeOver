# 작업 규칙 (Git/GitHub)

## 브랜치 전략

- `main`은 항상 빌드되는 상태로 유지한다. **직접 push 금지**
- 기능 작업은 브랜치를 따서 한다. 이름 규칙(예시):
    - `feature/기능명` — 새 기능
    - `fix/버그명` — 버그 수정
    - 예: `feature/portfolio-dashboard`, `fix/npc-memory-null`
- 브랜치 하나 = 작업 하나. 여러 기능을 한 브랜치에 몰아넣지 않는다.

## 작업 사이클

1. **작업 시작 전** — `main`으로 가서 `git pull`로 최신 상태 받기
2. 새 브랜치 따서 작업 (`git checkout -b feature/...`)
3. 커밋은 의미 단위로 쪼개서, 무슨 작업인지 알 수 있게 메시지 쓰기
4. 원격에 push (`git push -u origin feature/...`)
5. GitHub에서 **PR(Pull Request)** 생성 → `main`으로 머지 요청
6. 팀원 리뷰(또는 확인) 받고 머지
7. 머지 후 로컬 `main`도 다시 `pull`

## 커밋 메시지, PR 올릴 때

- PR 설명에 **뭘 바꿨는지 / 왜 바꿨는지** 간단히 적기
- 뭘 왜 바꿨는지 짧게: `기능: 지분 매입 UI 초안`, `수정: NPC 메모리 null 참조 오류`
- 세션/도구 이름 등 불필요한 접두사 없이 팀원이 봐도 바로 알 수 있게

## 코드 컨벤션

- **camelCase** — 변수·함수 이름. 첫 글자 소문자, 이후 단어 첫 글자만 대문자. 예: `myVariableName`
- **PascalCase** — 클래스·타입 이름. 첫 단어부터 첫 글자 대문자. 예: `MyClass`

## Unity 특이사항

- **씬/프리팹 동시 작업 피하기** — 같은 씬을 두 사람이 동시에 건드리면 충돌 나기 쉽다. 씬 단위로 담당을 나누거나, ~~작업 전 Discord에 "OO씬 작업합니다" 공유~~
- `.meta` 파일은 코드/에셋이랑 **항상 같이 커밋** — 파일 하나 옮기거나 이름 바꾸면 `.meta`도 같이 움직여야 참조가 안 깨짐
- 큰 바이너리(텍스처, 오디오, 대형 FBX 등)는 Git LFS 대상 — `.gitattributes`로 관리 (필요 시 추가)
- 작업 전 `git pull` 안 하고 시작하면 나중에 `.meta` GUID 충돌 같은 게 꼬이기 쉬우니 **시작 전 pull은 필수 습관**으로
